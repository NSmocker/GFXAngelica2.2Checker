# 07 — Пакетна перевірка GFX і результати

Стан на **2026-11-15**. Рендер: `GFXAngelica2.2Checker 0.4.0 (orbit viewer)`,
x64 Release, Direct3D 9, ассети `B:\Git\PW146RUUnpackedAssets\gfx` (9019 файлів).
Цей документ фіксує завершені прогони та їхні обмеження; артефакти містяться
в локальній `build/gfx-audit/`, яка ігнорується Git.

## 1. Що зараз перевіряє скрипт

`scripts/check-gfx.py` запускає справжній exe окремим процесом для кожного GFX.
Формат GFX читає рушій; Python аналізує збережені PNG через Pillow.
Вихідна роздільність — типові 512×512 у preview; крок симуляції — 50 мс.

- `VISIBLE`: процес завершився з кодом 0 і PNG містить хоча б один RGB-піксель,
  відмінний від чорного. Альфа не враховується.
- `EMPTY`: код 0, PNG є, усі RGB-пікселі чорні.
- `FAIL`: невдалий запуск/ненульовий код виходу або відсутній PNG.
- `TIMEOUT`: процес не завершився за відведений час; скрипт завершує його.

`VISIBLE` не доводить правильність усіх компонентів, матеріалів, анімації чи
кадрування. Один слабкий піксель або повністю пересвічений кадр також проходить
цю перевірку. `EMPTY` сам по собі не доводить помилку ассета: потрібні PNG, логи,
час анімації та аналіз потрібного ігрового контексту.

Offscreen-буфер очищується один раз перед циклом, як у ICL, і накопичує кроки.
Це не скріншот одного останнього кадру. `--retry-frames 100` повторно запускає
ефект від початку зі 100 кроками (5000 мс поданого часу); `PlaySpeed` може
змінити внутрішній час ефекту. У віконному режимі backbuffer очищується щокадру.

## 2. Запуск і повторення

Потрібні зібраний exe, його DLL, Windows ACP 936, Python 3 та Pillow.
Залежності/збірка: [04-build.md](04-build.md). Усі команди — з кореня репозиторію;
кожен прогін потребує нової вихідної теки.

```powershell
# Вибірка по верхніх папках, 10 кроків; порожні повторити зі 100 кроками
python scripts\check-gfx.py --out build\gfx-audit\sample-new --limit 240 --seed 20261115 --retry-frames 100

# Ті самі файли, що в контрольному прогоні
python scripts\check-gfx.py --out build\gfx-audit\regression-new --manifest build\gfx-audit\regression\manifest.json --retry-frames 100

# Повний набір: команда доступна, але повний прогін ще не виконано
python scripts\check-gfx.py --out build\gfx-audit\all-new --limit 9019 --retry-frames 100
```

| Параметр | Типове значення / поведінка |
|---|---|
| `--root` | `B:/Git/PW146RUUnpackedAssets`; сканується вкладена `gfx/` |
| `--exe` | `bin/x64/Release/GFXAngelica2.2Checker.exe` від кореня проєкту |
| `--out` | Обов'язкова тека; наявний `report.csv` не перезаписується |
| `--limit` | 48; верхня межа кількості файлів із дерева |
| `--seed` | Без значення — відсортовані файли; із seed — перемішування всередині груп |
| `--manifest` | UTF-8 JSON-масив шляхів відносно `<root>/gfx`; замінює автоматичну вибірку |
| `--frames` | 10 кроків початкової спроби |
| `--retry-frames` | 0, повтор вимкнений; повторюється лише `EMPTY`, якщо значення більше `--frames` |
| `--timeout` | 20 секунд на одну спробу |

Автовибірка бере по одному файлу з кожної верхньої папки за коло; файли в самому
корені утворюють окремі групи. `--seed` робить порядок повторюваним для того самого
набору файлів. Для точного повтору використовується manifest; `--limit/--seed` тоді
не визначають склад. Абсолютні шляхи до GFX передаються exe, зокрема для `gfx/gfx/`.
Це окремий пакетний інтерфейс: `--list` у exe досі лише друкує txt-список.

## 3. Артефакти та CSV

```text
<out>/
  manifest.json          список перевірюваних шляхів
  run.json               root, frames, retry_frames, seed, SHA-256 exe
  runtime/               копія exe/DLL, власні журнали прогону
  report.csv             один рядок на файл, UTF-8 BOM, роздільник ;
  summary.json           кількість VISIBLE/EMPTY/FAIL/TIMEOUT
  contact-001.png ...    огляди по 48 результатів; номер відповідає idx у CSV
  00001/
    frame.png
    stdout.log, stderr.log, checker.log, A3D.log/AF.log/AM.log (якщо є)
    retry/               друга спроба з власними PNG/логами, якщо потрібна
```

CSV: `idx;file;status;exit_code;seconds;frames;attempts;nonblack;maximum;png`.
`frames`, піксельні метрики, статус, код і PNG описують останню спробу;
`attempts` — кількість спроб, `seconds` — сума часу запусків із очікуванням.
`png` відносний до `<out>`. Перша спроба зберігається. Оглядові PNG показують
останню спробу, а не вибирають найкрасивіший кадр.

Кожен прогін копіює готовий exe/DLL до початку роботи, тому наступна збірка не
підмінює його посеред перевірки. Журнали різних прогонів розділені.
У C++ `checker.log` є параметри GFX/камери/AABB, сумарні лічильники рендеру,
типи/активність елементів, результат завантаження SMD та `PNG pixels: …`.
Навіть після повідомлення `EMPTY` успішний запис PNG завершує exe з кодом 0.

## 5. Що виправлено і що лишилося

Виправлення в поточному коді:

1. `LC_CTYPE=".936"` відокремлено від `LC_NUMERIC="C"`. Регіональна кома більше
   не ламає `sscanf` координат і параметрів GFX із десятковою крапкою.
2. Кадрування враховує центр і масштаб AABB, near=0.2, пропорції viewport;
   використано патерни `AUIModelPicture` і ICL.
3. Додано обидві 2D-черги, реальний розмір прихованого вікна та центрування 2D.
4. SMD завантажуються через `A3DSkinModel`; світло/земля адаптовані з редакторських
   callback-ів. У логах підтверджене завантаження `gfx\Models\烟花\烟花.SMD`.
5. Resolver зберігає справжній шлях `gfx/gfx/`; з'явилися піксельна діагностика
   та пакетний скрипт із повтором порожніх кадрів.

П'ять порожніх результатів контрольної вибірки:

| idx | GFX | Стан розбору |
|---:|---|---|
| 4 | `sgc\刺客_致盲_技能击中.gfx` | Сценарій навички; loader окремого GFX повернув 0 елементів. Потрібне розпізнавання/відповідний runtime. |
| 11 | `无标题.gfx` | Елемент із `Warp: 1`; окремий warp-прохід не підключений. |
| 12 | `武器轨迹\刀光白.gfx` | Слід зброї без руху власника; контекст анімації ще не відтворюється. |
| 23 | `武器轨迹\剑光蓝.gfx` | Те саме обмеження сліду зброї. |
| 34 | `武器轨迹\匕首红.gfx` | Те саме обмеження сліду зброї. |

`程序联入\人物游动水圈.gfx` з'явився на повторі: `PlaySpeed=0.5` і
`EmissionRate=3` давали лише 250 мс часу ефекту за перші 10 кроків.

28 порожніх файлів розширеної вибірки: 12 у `武器轨迹`, 8 у `烟花`, 3 у `界面`,
2 у `npc`, 1 у `场景`, сценарій `sgc` та `无标题.gfx`. Це розподіл за папками,
а не підтверджений діагноз для кожного. Зокрема `界面\2012登陆界面_登陆框.gfx`
завантажує три SMD, але лишається порожнім із дуже великим 2D-AABB; потрібен
подальший розбір кадрування. Причини решти не оголошуються виправленими.

ECM-менеджер, warp, сценарії навичок, рух власника, runtime світу й lost-device
залишаються відкритими. Наявність `VISIBLE` також не виключає частково відсутніх
компонентів, обрізаного ефекту чи пересвічення від накопичення кадрів.
Подальші роботи — у [плані](05-implementation-plan.md).
